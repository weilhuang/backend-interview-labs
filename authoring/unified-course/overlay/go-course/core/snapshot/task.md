# C13-04 切片、map 与数据所有权：为什么快照被改了？

本任务的原生Go工程在 `go/`。下面的源码路径以该Go工程为基准；第一次运行先进入 `go/`。Java文件只是公开判题桥，不是本题要填写的内容。

## 先看到问题，再修复

你负责一个订单服务。下单时把订单交给发货环节；用户后来修改购物车，不应改变已经生成的发货快照。这节不需要 Docker、数据库、前端框架或网络服务。

你会修改 `snapshot.go` 的 `SnapshotOrders`。模型、完整调用方、全部测试和两份参考解都已给出。起点能编译、能运行，但只复制了最外层，因此有意留下可观察的业务缺陷。不要把起点测试失败当环境坏了。

先在终端进入本目录，确认 `go version` 真正输出 Go 语言工具链版本。本题使用 Go 1.27.1；Go 编辑/调试与主 Java Academy 课程的原生检查仍需单独验证。`go.mod` 的 1.26.0 是语言最低版本声明，实际运行工具链须为 Go 1.27.1。

```sh
cd go
go run ./cmd/observe
go run ./cmd/demo
go test -count=1 ./...
```

`observe` 不调用待修函数，始终可运行。你应看到：修改 b 会影响 a；把元素复制到 c 后，修改 c 不影响 a。`demo` 调用的就是你的实现，起点会把快照中的数量也变成 2、标签变成“活动价”、状态变成“已付款”。修复后 live 仍会改变，但 snapshot 应保持数量 1、标签“原价”、状态“待付款”。

完整路径：`cmd/demo/main.go → Demo() → SnapshotOrders(live) → 修改 live → JSON 输出`。业务调用方在 `demo.go`，测试在 `snapshot_test.go` 与两个 `cmd` 目录。可以逐个打断点，不存在隐藏调用者或隐藏测试。

## 进入这节前要懂什么？

只要求能读函数、结构体、for/range、返回值。如果下面三项不确定，先看 [语法补课](go/docs/语法补课.md)：

1. `[]Order` 是“Order 的切片”，不是 Java 数组语法
2. `make([]Order, n)` 创建长度为 n 的切片；`copy` 复制元素值
3. `map[string]string` 用字符串键查找字符串值；给 map 变量赋值不会复制全部键值

不要求先会指针算术、goroutine、泛型或 Go 运行时源码。

## 公开函数合同

```go
func SnapshotOrders(src []Order) []Order
```

- C1 值与顺序：返回内容与调用瞬间的输入相同，订单、明细、标签顺序保持；不丢字段
- C2 nil 与空：每一层都保留 nil 或“非 nil 的空容器”。这是一项明确的业务合同，不是说两者在所有程序里都必须区分
- C3 双向隔离：返回后修改输入，不影响输出；修改输出，也不影响输入。覆盖顶层订单、明细、标签、map 的新增/更新/删除和切片 append
- C4 各份独立：两次调用返回的快照相互独立；输入两个订单即使共用一个 map 或明细切片，输出两个订单的可变部分也分别独立
- C5 无副作用：复制过程不能修改、排序或清空输入
- C6 不做别的：不清洗字符串、不算价格、不校验订单、不启动后台任务。输入可含任意 Go 字符串，原值保留

调用期间，其他 goroutine 不得并发修改输入。本函数没有锁，也不能把正在被并发写入的 map 安全变成快照。这个前置条件会在并发模块重新讨论。

本题模型没有循环引用、指针字段或接口；不是“通用深复制框架”。增加字段后，需要重新审查所有权边界。

## 阶段一：最外层复制为什么还不够？

打开 `snapshot.go`，现有代码的意思是：

1. 输入 nil，直接返回 nil
2. 给结果准备一个新的订单切片
3. 把每个 Order 的值复制过去

运行：

```sh
go test -run 'TestSnapshotContract/CP1_' -v .
```

起点这一组应通过。这只能证明顶层字段的隔离，不能证明订单内部所有内容都隔离。接着运行：

```sh
go test -run 'TestSnapshotContract/CP2_LineOutputToInput' -v .
```

读断言：“明细切片仍共享底层数组”。在 `model.go` 看 `Lines []Line`。Order 值被复制了，但 Lines 仍描述同一组明细元素。

```text
顶层复制之后：
输入 Order ── Lines ─┐
                    ├── 同一组 Line ── Tags ── 同一组标签
输出 Order ── Lines ─┘

输入 Order ── Metadata ─┐
                       ├── 同一个 map
输出 Order ── Metadata ─┘
```

ASCII 图中的线表示“仍访问同一份可变数据”，不是语言规范承诺的具体内存布局。渲染图见 [PNG图](go/diagrams/ownership.png) 与 [SVG图](go/diagrams/ownership.svg)。

## 阶段二：每个可变容器各有自己的存储

先只解决 `Lines`：遍历订单，对于非 nil 的明细切片创建新切片，复制每条明细。不要一上来同时改所有层。再跑上面的单个测试，它应由红转绿。

接着跑 `CP2_TagOutputToInput`。如果它还红，这是正常的新信息：Line 内部又有 `Tags []string`。再为非 nil 标签切片准备独立存储并复制元素。

最后处理 Metadata：非 nil 时创建新 map，用 range 复制每个键和值。字符串不提供原地修改字节的普通操作，本题字符串按值复制即可，不需要逐字节重建。

```text
完整复制之后：
输入 Order ── 原 Lines ── 原 Tags
          └── 原 Metadata

输出 Order ── 新 Lines ── 新 Tags
          └── 新 Metadata
```

每修一层跑一组：

```sh
go test -run 'TestSnapshotContract/CP2_' -v .
```

为什么先判断 nil？若直接对 nil 输入执行 make，结果会变成非 nil 空容器；若用 `append([]string(nil), empty...)`，非 nil 空标签反而可能变成 nil。本题明确保留这一区别，测试会指出违反 C2。

## 阶段三：从“看起来一样”到“确实独立”

单看返回值相同，不足以证明隔离。打开下面三个可见反例：

- `CP3_SharedInputContainersSeparate`：两个输入订单原先共用 map/标签。输出第一份被改后，第二份也不能变
- `CP3_SpareCapacityAppend`：输入切片长度为 1，容量允许更多元素。错误实现可能在 append 时覆盖输入的隐藏尾部
- `CP3_NoMutationDuringCall`：有的实现先改输入再复制，结果表面上“相等”，但违反了无副作用合同

现在跑全部用例并重新运行调用方：

```sh
go test -count=1 ./...
go vet ./...
go run ./cmd/demo
```

期望：所有测试通过；live 显示购物车新值，snapshot 保留发货时旧值。测试失败要修实现，不删除断言，不把测试改成你的输出。

支持 race detector 的平台还可运行 `go test -race ./...`。本节不包含并发写输入的承诺；race 没报警也不等于任意使用方式都线程安全。
