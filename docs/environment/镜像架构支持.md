# 共享镜像的 CPU 架构支持

**结论：当前台账的 7 个镜像均发布了 Linux amd64 与 arm64 manifest。** Apple Silicon 使用原生 Linux arm64 Docker daemon 时，没有发现因这批镜像缺少 arm64 而必须更换版本或启用 amd64 仿真的理由。固定 Maven digest 是多架构 index，不是单独的 amd64 manifest。

这是一份**发布元数据核验记录**，不是 Mac 实机测试报告。Mac Intel、Apple Silicon 上的启动、业务读写、消息收发、重启持久化、绑定挂载及资源峰值均未因此得到验证。已有 Linux amd64 实际 CI 证据另见[验证记录](verification.md)，发布验收要求见[运行契约](runtime-contract.md#4-发布前必须完成的实机验收)。

- 只下载 JSON 元数据，未下载镜像层、创建容器、安装软件或操作个人 Mac。OCI index 中的 `unknown/unknown` 证明材料不是可运行 CPU 平台，本记录只摘录 amd64/arm64 项

## Mac 使用与 doctor 提示

Compose 不强制 `platform`，同一引用由 Docker 按 daemon 平台选择对应镜像。多架构标签无需同时下载两个 CPU 的镜像层，也无需维护一套 Mac 专用版本；仍只启动当前课程需要的 profile。[Docker 官方多平台说明](https://docs.docker.com/build/building/multi-platform/)

`./scripts/lab.sh doctor` 区分脚本主机和 Docker daemon 的架构，将 `aarch64`/`arm64` 归为 `arm64`，`x86_64`/`amd64` 归为 `amd64`。判断使用实际 daemon 信息，而不以运行脚本的主机或 Mac 芯片猜测远程 daemon。

doctor 还明确展示 `DOCKER_DEFAULT_PLATFORM`。如果显式覆盖的系统/CPU 架构与 daemon 不匹配，会提醒仿真可能更慢、占用更多资源或无法运行；**只警告并保留覆盖值，不修改用户 shell/Docker 设置、不删除环境变量、不启用模拟器**。未知架构或格式不能被当成匹配。相同系统/CPU 也不证明任意平台变体均可运行。

该变量确实影响 Compose 镜像拉取：见[Docker CLI 官方变量说明](https://docs.docker.com/reference/cli/docker/#environment-variables)，以及仓库 CI 使用的 [Compose v2.38.2 官方源码](https://github.com/docker/compose/blob/v2.38.2/pkg/compose/pull.go#L338)。因此即便 Compose 文件没有 `platform`，也不能忽略用户环境中的显式覆盖。

doctor 不自动访问 Registry 或拉取镜像；本页是已完成的独立元数据审核。doctor 成功仅说明其版本、daemon、Compose 解析等检查通过，不代表业务 smoke、Mac 实测或实际峰值验收通过。

## 固定版本与剩余边界

1. 本次没有改动台账、Compose、镜像版本或 CI。Maven 已按 index digest 固定；其余六项仍锁完整标签，标签可以被上游重建，后续查询应核对这里记录的时间与 digest
2. 将其他 index digest 写入台账必须走现有版本升级/回归流程，不能把本次元数据快照冒充原 CI 已运行的精确镜像身份
3. Apple Silicon 与 Intel Mac 均仍需按运行契约实测。arm64 manifest 存在不证明脚本、JDK、本地文件共享、Testcontainers 集成及业务客户端全部兼容
4. 资源表是规划预算；本次未测 Mac CPU、内存、磁盘峰值。低配置机器继续单组件/单阶段运行，不并发重型中间件和 Java 构建
5. 元数据支持不意味着版本最新、受维护或无漏洞。尤其 Testcontainers 的临时旧版 Alpine 仍受[既有安全边界](verification.md#testcontainers-辅助镜像)约束
