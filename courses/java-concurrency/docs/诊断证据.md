# 虚拟线程诊断：采集不等于解释

## 安全边界

scripts/diagnose.py只启动/采集/终止自己创建的子进程，不接受用户PID、不连接真实业务、不生成heap dump。JVM堆96MiB、8请求、2下游并发、等待最多15秒、JFR上限8MiB，脚本命令各自有超时。发生失败先保存report，再终止子进程。只删除build/diagnostics中的自己实验文件即可清理，不清空其他目录。

```sh
JAVA_HOME=/path/to/jdk-21 python scripts/diagnose.py
```

预检要求完整JDK21的java/javac/jcmd/jfr。若Attach受平台限制记BLOCKED，不把采集失败当成学生知识错误。

## 实验逻辑

```text
8个虚拟任务 --> 2个持有下游许可，在release latch等待
            --> 6个等待Semaphore许可
脚本确认READY --> 采集平台线程栈 + 全线程JSON --> 发送换行
             --> 放行全部工作 --> 核对合计28 --> 保存JFR并退出
```

这不是死锁：存在可执行的外部放行操作。为制造真正池耗尽/锁环应在JVM课程的独立有界实验中进行，不能把永不结束的进程留在机器上。

## 产物与如何读

- ready.txt：准确PID与已到达的控制点；不能对着历史PID采集
- platform-threads.txt：传统Thread.print；在21中不能把它当全部虚拟线程清单
- all-threads.json：Thread.dump_to_file的结构化线程转储；找到虚拟请求栈，识别Semaphore与CountDownLatch等待位置
- recording.jfr：实际采样；jfr-summary.txt列出事件数；jfr-events.txt只打印相关事件
- process.log：业务合计与退出结果；report.json记录环境/上限/执行状态

先找两个等待release的任务，再找等待下游许可的任务，说明谁能使系统前进。ThreadPark事件显示过的等待不能单独证明现在仍等待；线程转储是瞬时样本。JFR事件可能未开启、阈值未满足、采样期不覆盖、版本事件不同，不能将零事件解释为没有问题。

## 固定版本下的pinning阅读

OpenJDK21 GA基线中，某些synchronized内阻塞/native调用可能限制虚拟线程卸载；相关实现查看VirtualThread.onPinned与JEP444。后续JDK相关机制可能改变，本课不把21结论扩展到所有版本。默认实验不人为制造高负载pinning，jdk.VirtualThreadPinned为0是合法结果，必须如实记录。

## 平台池与虚拟线程对照（O）

使用相同8请求、2下游许可、相同固定业务结果和相同协调输入。一次只改执行方式，记录JVM版本、核数、堆、请求数、下游容量与等待时间。重复多轮记录分布；不要把控制脚本/jcmd的耗时算成业务延迟，也不要从8请求演示推导生产吞吐优劣。CPU密集型再单独设计同样工作量的有界对照，不把两类工作混测。

## 人工验收问题

1. 为什么六个任务等待不等于死锁？谁持有/归还许可？
2. 如果数据库连接池只有一条，两个下游许可是否还有效保护最窄瓶颈？
3. Future被取消后，哪个证据能证明业务finally已完成？
4. 如果请求永不响应中断，当前封装的关闭返回什么，生产系统需要哪层deadline？
5. 你观察的线程栈和JFR事件是否来自同一时间窗？还存在哪些替代解释？

至少提供一条完整“症状→候选机制→证据→排除→修改→回归”的因果链。自动脚本只验证产物和业务不变量，诊断结论由人评阅。

## 已提供的完整对照调用程序

scripts/BoundedBlockingComparison.java提供平台固定池与虚拟线程两种模式，使用相同16请求、2下游许可、40毫秒合成阻塞时间。有限sleep代表负载等待，不用于测试同步；正确性仅核对最大资源并发和最终许可，延迟数字只作O类证据。

```sh
mkdir -p build/comparison
javac --release 21 -encoding UTF-8 -d build/comparison scripts/BoundedBlockingComparison.java
java -Xmx96m -cp build/comparison BoundedBlockingComparison platform
java -Xmx96m -cp build/comparison BoundedBlockingComparison virtual
```

排队延迟从提交计入，每种模式独立启动JVM。单次16请求的P95十分粗糙，不作统计显著性结论。要研究吞吐优势，先明确相同的下游容量和延迟约束，再设计多轮、有预热的测量；增加虚拟线程数不能绕过此处2个下游许可。
