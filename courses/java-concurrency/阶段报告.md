## 2. 详细教学内容

### C02-01 JMM与安全发布

[题目与完整答案](juc/01-publication/lab/task.md)。用不可变配置快照和volatile引用维护“同一代版本/路由”的一致读取，record内部列表做防御性复制；原子计数返回唯一序号。另有CyclicBarrier固定两次读取先于写入，确定复现volatile复合操作丢更新。特别说明：同步测试读到正确值不能证明去掉volatile也正确，未观察到重排不是不存在。面试追问final语义、this逃逸、深不可变与多字段业务不变量。

### C02-02 线程生命周期与协作取消

[题目与完整答案](juc/02-cancellation/lab/task.md)。工作者分开记录开始、业务故障、清理完成。cancelAndAwait校验预算、发中断、等清理后的完成信号；零预算不等待、未响应中断不能返回假成功。测试通过latch操纵正常等待、异常、忽略第一次中断、重复启动，最终释放所有测试线程。讲清传播InterruptedException与恢复标记的不同边界。

### C02-03 monitor与显式锁

[题目与完整答案](juc/03-bounded-buffer/lab/task.md)。同一FIFO/容量/关闭合同分别实现synchronized-wait-notifyAll和ReentrantLock-Condition。关闭后排空、不接新元素、唤醒全部生产者/消费者；等待必须while重检，显式锁finally释放。对照JDK ArrayBlockingQueue并明确其没有本题close语义；讲条件队列与同步队列、公平性与吞吐、死锁顺序。

### C02-04 AQS与同步器源码

[题目与完整答案](juc/04-aqs/lab/task.md)。用AQS共享模式写一次性门，验证打开幂等、零预算、所有等待者释放、中断不消耗资格。真实CountDownLatch记录完成数、Semaphore约束同时进入数。源码走ReentrantLock.initialTryLock/AQS.acquire、释放和共享传播，避免把旧版队列字段硬套到21。已实际用jdb命中真实AQS.releaseShared，保存业务调用栈与state=0的[实测记录](docs/实际调试记录.md)。

### C02-05 CAS与并发容器

[题目与完整答案](juc/05-atomics/lab/task.md)。CAS额度预留必须失败重读，不透支，添加溢出不改状态。ABA用固定A→B→A历史对比AtomicReference与AtomicStampedReference，明确引用身份和版本溢出。CHM+LongAdder计数只保证写者结束后的精确合计，不把运行中的sum当事务快照；讲并发remove后旧计数器引用的业务边界。

### C02-06 线程池容量保护

[题目与完整答案](juc/06-executor/lab/task.md)。有界队列配AbortPolicy，测试精确控制“核心线程→排队→最大线程→拒绝”。通过Future观察任务异常，取消队列项回收容量；优雅期限到后shutdownNow，并取消它返回的未启动Future，防止调用方永远等待。源码同时跟execute/worker与submit/FutureTask两条链，解释CallerRuns、Discard和无界队列的代价。

### C02-07 CompletableFuture与上下文

[题目与完整答案](juc/07-futures/lab/task.md)。主服务失败立即失败，次服务失败显式降级，总期限由可注入Timer驱动。手动计时器让测试无需sleep；显式Executor与Semaphore隔离，ThreadLocal在finally恢复原上下文。新增确定性测试：聚合已经超时，底层业务仍未完成且仍占许可；真正退出后下一请求才能进入。取消结果Future不自动中断底层动作，课程对此给出反例。

### C02-08 虚拟线程与诊断

[题目与完整答案](juc/08-virtual-threads/lab/task.md)。每任务虚拟线程仍受受理上限/下游许可限制；最多64受理任务、16下游并发。关键审查修复：FutureTask.done可能在运行中取消时提前调用，不能在那里无条件释放受理容量。实现区分尚未启动取消与运行中取消，只释放一次；运行中必须等实际run退出。对应测试刻意忽略第一次中断，Future虽isDone，新的submit仍被拒绝，最后由latch安全放行。

提供同负载平台池/虚拟线程完整对照程序和受限JFR/线程转储脚本，区别资源正确性A与性能/事故解释O。Java21的pinning结论有版本边界，不宣称适用于所有后续JDK。

## 3. 代表源码与质量设计

### 为什么取消完成不能当作实际退出

本节真实实现的关键结构如下（完整代码可在题目与src中查阅）：

```java
public void run() {
    if (!phase.compareAndSet(0, 1)) return;
    try {
        super.run();
    } finally {
        phase.set(2);
        releaseAdmission();
    }
}

protected void done() {
    // 运行中取消只结束Future；许可必须等真正的run退出才归还。
    if (phase.compareAndSet(0, 2)) releaseAdmission();
}
```

状态0是尚未启动，1是正在执行run，2是实际结束或启动前取消。正确替代解用synchronized保护同一生命周期，证明没有靠私有字段布局强迫单一实现风格。错误变体恢复“done立即释放”，会被忽略中断的确定性测试杀死。

### 测试为何能说明问题

- lost-update由barrier固定交错，不重跑直到碰巧失败
- 线程池饱和由任务启动/释放latch固定，拒绝不是靠sleep猜满
- deadline由ManualTimer显式触发，无需等真实秒数
- 线程/锁等待都有2–3秒保护，超时只防挂起，不是性能SLA
- 并发集合最终统计等全部Future完成，再断言精确值，不要求运行中原子快照
- 源码和诊断解释采用人工证据rubric，自动脚本不以关键词或速度阈值假装理解
