# 盲测变体与公开评估标准

先用scripts/draw-defense.py抽取一组题，独立完成代码、回归和口述，再对照本文件。标准解始终可读，不设置隐形门槛。自动测试证明的是合同案例，独立掌握仍需要真实试学记录。

## 四个故障问题的参考推理

HTTP提交后丢响应：先查原请求号。不存在也不能武断推出此前绝未提交，要考虑查询发生的时间；同号重试由唯一键和参数合同决定，不换新号。新增回归要断言库存只扣一次、outbox只有一个v1。

outbox已标记但inbox为空：该标记只说明Kafka确认，不能证明消费RPC已经完成。检查消费组位点、接收端可用性与日志；恢复后重放。同号不同载荷是错误，不能通过清空inbox“修复”。

Redis旧值：写后删缓存不能阻止正在进行的旧查询在删除之后回填。TTL限制每次写入的缓存寿命，晚回填可能延长相对提交的陈旧窗口，fresh查询读事实；更强要求可引入版本栅栏，必须再验证版本推进与崩溃窗口。

取消乱序：版本2的取消先到时，读模型保存2；后来的1只记去重，不覆盖状态。事件号校验和载荷比对防止相同身份换含义。真实实物已发货后的取消不是本状态机能够直接处理的业务，需要新状态和补偿合同。

## 四个新需求的参考改法

新增pen：只在独占测试fixture插入initial_stock=10,available=10；代码按sku条件更新，不应增加Java分支。并发book与pen，分别断言守恒。学习者Compose数据若需插入，应明确仅在课程库增加新商品，不重置现有库存。

最大20件：OrderRules数量上界改20，补19/20/21测试；检查原号参数冲突仍生效。超卖约束不依赖这个上界，不能删除数据库条件更新。

审计排序：先创建可变局部列表，再用severity优先级映射(ERROR=0,LAG=1)和subject比较器排序，最后List.copyOf。比较器应传递且稳定；新增相同severity不同subject和不可变结果测试。

缓存命中来源：增加QueryResult(Order order,String source)，仅查询接口返回；cacheHit标CACHE，数据库读标DATABASE。source是一次路径的事实，不能代表最新版本。禁止在place或cancel里读取Redis决定库存。

## 四个设计问题的参考边界

高并发热点SKU：先测事务持有时间、行锁等待、成功/拒绝率、p99与连接池饱和，区分吞吐与业务成功。优化可考虑队列、预分配或批量，但每个方案都必须重述不超卖与取消补偿合同，不能先拍脑袋加线程。

拆成两个数据库：当前一致性审计快照不再涵盖两边。订单库存本地守恒仍可精确验证，跨库投影需记录源版本/水位与延迟窗口；不能比较不同时间点后把正常延迟判为数据损坏。

回收幂等：先约定客户端和消息最大重放期，结合归档、墓碑或业务代际拒绝迟到身份。只设置Redis TTL会让过期请求再次执行，不能作为持久幂等的充分实现。

单broker的acks=all：它仅确认当前ISR，单节点并不具备副本故障容忍。必须给出副本数、min.insync.replicas、故障拓扑和实测证据，才能讨论高可用结论。

## 2分钟陈述样稿

我做的是隔离的订单库存实验，不接真实支付。核心合同是库存不为负、同请求不重复扣、取消只补一次、读模型不被旧事件倒退。订单、库存和outbox同MySQL事务；Kafka和gRPC的确认丢失允许重放，接收端用inbox和版本保护效果。我分别检查了快测、真实服务和浏览器结果，具体通过状态见阶段报告。这个单机拓扑没有证明生产容量或多可用区容灾。

## 5分钟结构

前2分钟说清问题与不变量；第3分钟画出数据库commit、Kafka确认、接收端commit和消费位点四个边界；第4分钟讲一个实际跑过的故障，给出请求号、行数和恢复证据；第5分钟解释Redis旧值、软准入阈值、单broker和共享MySQL实例的取舍。不要把还没跑的CI说成亲测。

## 15分钟结构与追问

0–2分钟业务合同；2–5分钟状态机与事务SQL；5–8分钟用一个确认丢失实验展示重放；8–10分钟追踪KafkaConsumer.commitSync、gRPC deadline与MySQL事务；10–12分钟展示一次新变体回归；12–15分钟比较其他方案并列出容量、故障域和独立试学尚未证明的部分。

评分关注：是否先给假设、是否区分未知与失败、是否用可检查证据支持因果、是否守住单调性和守恒、是否主动说清限制。背出组件名称或只展示绿色数量不计入这些能力。
