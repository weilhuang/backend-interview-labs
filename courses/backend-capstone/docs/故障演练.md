# 从症状到回归的事故记录

这些命令只作用于本课程的Compose项目。先保存请求号；不要重置数据库或删除卷。默认手动调用重放，让每个确认窗口可见；没有后台任务替你悄悄改变观察状态。

## 演练一：订单提交后客户端结果未知

先运行02-reliability的真实测试。AFTER_ORDER_COMMIT在数据库commit之后抛Unknown，不伪造rollback。记录库存下降、订单存在、outbox存在；用原号原参数重试，结果相同；用新号会成为新订单。这是客户端超时后的恢复合同，不是随机sleep碰运气。

## 演练二：配送服务停止

1. start后提交book两件，不先重放，保存请求号和dashboard
2. `bash scripts/course.sh pause-service delivery`
3. 刷新页面，应显示RPC不可用。POST replay可能已经把outbox标记已发布，然后在RPC处失败
4. 确认订单没有消失，投影落后数大于0；outboxPending为0不能作为完成证明
5. `bash scripts/course.sh recover-service delivery`，再重放
6. 同一请求投影追平，inbox事件数不会因重放无界增长，Audit没有ERROR

假设“订单事务已失败”与证据冲突，因为源表已提交；正确定位是接收端确认没有完成。生产中的永久坏消息需有审计的隔离流程，本实验中止整轮消费供诊断，失败位点不提交，其他分区也可能暂时受阻，不自动丢弃。

## 演练三：MySQL重启

提交订单并记录当前库存、事件数，暂停mysql；数据库不可用时/api/ready应503，不能用缓存状态判定能可靠写入。recover-service mysql后，Hikari应恢复新连接，源表和未发送事件仍存在；重放后读模型追平。

Testcontainers恢复用inspect重新读取随机端口，不假定重启后的映射永不变化。Compose服务内部用mysql:3306，不受本机随机端口影响。保留容器卷只证明这个恢复场景，不证明宿主机故障或卷损坏时的数据安全。

## 演练四：Redis停止与旧值窗口

先缓存查询，再暂停redis；强一致查询与取消仍用MySQL。缓存失败不能rollback已提交订单。恢复缓存后，TTL范围内可能读到旧状态；fresh=true立即读事实。请画出“旧读开始→取消commit→删缓存→旧读回填”的竞态，说明为什么本策略只是可能暂时陈旧，而不是强一致缓存。

## 证据模板

- 环境：JDK完整版本、Gradle、镜像快照SHA、Git提交、Docker/Compose版本
- 初始事实：请求号、库存、订单状态/版本、outboxPending、projectionLag、inboxCount
- 故障命令与预期：哪个持久化边界已经完成，哪个确认还未知
- 实际观察：命令退出码、HTTP状态、SQL行数、Kafka消费组位点和探针
- 恢复：只恢复故障组件，使用原身份重放
- 回归：库存守恒、取消只释放一次、重复事件不重复作用、投影单调
- 未验证：副本丢失、多机网络分区、宿主机损坏、真实生产容量等，按实际填写

## 跨Java进程的自动恢复验收

作者CI运行`python3 scripts/recovery-check.py`：先提交独占请求，再对本项目orders容器SIGKILL并重建，验证原订单事实仍在；随后杀停delivery，重放必须失败且保留投影落后，恢复后按原身份重放并取消。这个脚本没有在任意PID上发信号，也不会杀停MySQL或删除卷。

这里的进程故障发生于订单HTTP确认之后或配送RPC调用之前；精确“commit之后、应答之前”的窗口由可重复故障钩子覆盖，不声称SIGKILL脚本精确击中了任意机器指令。两个层次证据应分别记录。
