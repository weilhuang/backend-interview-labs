# C14 综合项目制作阶段报告

日期：2026-09-30。交付对象是完整V1中的C14五阶段课程，不是整套V1完成声明。本文让审阅者不用先运行项目，也能判断课程内容、业务合同和验证边界。

## 本批实际形成的内容

这是一套可编译、可运行、有前端调用入口的订单库存应用。五个检查点分别让学员实现需求合同、MySQL事务、消息确认顺序、恢复决策和数据审计。每节可作为课程内独立模块编译与练习，其他阶段以可读标准实现提供；本节目标类的参考副本从编译输入排除，防止测试绕过学生代码。

完整应用包含Spring Boot HTTP服务、MySQL订单/库存/outbox、Redis查询缓存、Kafka日志、独立gRPC配送进程、inbox和版本化读模型。预置中文页面直接调用这些接口，不提供静态假数据。学员无须先写前端，也不用复制上一节未完成的代码。

所有手写叙事、标题和注释为中文；技术标识符保留原名。固定protobuf工具生成的协议文件保留工具声明，出处在源码与版本文档。全部测试、调用方、公开参考类及每节完整标准答案直接可见，无解锁条件，也不从导出登记里排除答案。

## 项目结构与实际业务边界

`app/`是完整应用和中文页面，`reference/`是公开的五个标准类；`capstone/stages/`是五个独立学习模块；`shared/`是可见测试夹具与机器生成的镜像台账快照；`protocol/`保存gRPC合同；`scripts/`提供启停、HTTP验证、浏览器验收和随机抽题；`authoring/`保存元数据与正反解验证；根Compose负责真实服务。

```text
HTTP下单
  -> [唯一请求 + 条件扣库存 + outbox] 同一MySQL事务
  -> Kafka确认
  -> 标记outbox已发布
  -> 消费者调用独立gRPC进程
  -> [inbox + 单调版本配送投影] 另一MySQL事务
  -> 提交下一条Kafka位点
```

订单只有RESERVED与CANCELLED。预留可以取消，取消最多释放一次；实验不涉及真实支付、个人资料或不可逆实物发货。两个Java进程共享一个教学MySQL实例，但没有跨RPC共享事务。Kafka为单broker，这个拓扑不证明副本容灾或生产容量。

Redis只加速查询：提交后尽力失效，TTL五秒，失败回源；旧读回填仍可能短暂出现旧状态。强一致查询、库存判断与审计都绕过缓存。业务准入把待发布事件与落后投影都计入观察水位，水位是并发下的软阈值，不是假装精确的全局配额。

## C14-01：从需求到可反驳合同

学员编写OrderRules的参数验证、重复请求判断和取消迁移，共三个学习区。数量范围1–100、身份区分大小写、禁止空白/控制字符；同号同参数返回原订单，包括已取消状态，同号换商品或数量必须冲突。

代表练习不是“写个DTO”，而是回答：客户端收到超时后，如何分辨失败与结果未知？题目要求构造一个已取消订单，用原号再次下单时保持CANCELLED，不能因为重复请求而复活资源占用。

源码任务跟踪OpenJDK21 Objects.requireNonNull，并在领域验证分支设置断点，记录空引用、非法数量与业务冲突的区别。面试递进从请求号用途，走到参数冲突、失败结果是否永久幂等，再追问去重记录的回收窗口。

## C14-02：真正的事务与缓存取舍

学员编写下单与取消两个完整事务。核心SQL是条件扣减：`available=available-? WHERE sku=? AND available>=?`。唯一订单身份、库存修改、outbox追加共同commit；任何中间失败都rollback。MySQL1062单独识别，回滚后锁读已提交订单并比较参数，不能把任意SQL异常当成功重试。

代表回归用独占MySQL启动40个不同请求争抢16件库存，断言只有16个成功；另检查原请求响应丢失后的同号重试、Case/case身份独立、取消只释放一次以及Redis停止时业务仍能提交。这些真实MySQL断言与容器代码已提供；另用12路屏障并发同号下单和并发取消，分别断言只扣一次和只还一次。这些真实场景在第二轮CI实际通过，准确提交与仍失败的前端门禁见文末，不能由H2快测代替。

源码阅读对照Spring6.2.19 DataSourceTransactionManager的doBegin/doCommit/doRollback。本课显式使用JDBC暴露事务边界，避免把注解代理当作魔法。需要给出主键和outbox_pending查询计划，说明8连接池只是实验预算，容量结论需用等待、超时与p99数据支持。

## C14-03：每个确认窗口都能解释和重放

学员实现publishOne和consumeOne两个关键确认顺序。真实外层调用是KafkaProducer/KafkaConsumer与生成的gRPC stub；回调式快测只证明先效果、后确认的控制流，实际网络和持久化另设集成测试。

四个故障点明确可注入：订单commit后丢HTTP应答、Kafka确认后未标记outbox、接收端inbox事务commit后丢RPC应答、RPC成功后未提交消费位点。相同事件号同载荷幂等，换载荷拒绝；新增身份先投递v2、再投递尚未进入inbox的v1，覆盖真正的版本防倒退分支；另外同分区三条事件在第二条RPC失败后检查精确已提交位点，防止误提交整个poll批次。

代表问题：“DEADLINE_EXCEEDED是否可以立即补库存？”标准推理是服务端可能已提交，应按同一事件身份重试或查询，不能把未知当作失败。源码任务定位Kafka3.9.1 KafkaConsumer.commitSync和gRPC1.71.0 ClientCalls.blockingUnaryCall，在接收commit与位点确认之间抓证据。

发布、消费和网络超时有预算；Producer/Consumer关闭也有界。永久坏消息不会自动跳过，它会保留证据并中止本轮消费，其他分区也可能暂时受阻，生产化隔离队列是需显式设计的后续取舍。

## C14-04：完整事故恢复，而不是重启截图

学员实现数据库、缓存、下游依赖和积压阈值的决策矩阵。数据库不可用必须拒绝可靠写入；Redis失败可降级；Kafka/RPC失效时允许预算内保留outbox；达到阈值拒绝新单，取消仍可执行。

Compose通过真实探针等待MySQL、Redis、Kafka、配送RPC与订单HTTP。文档提供“发现→假设→验证→修复→回归”全过程，特别要求区别outbox已经发布与下游业务已经完成。真实MySQL重启用例保留数据层，重新inspect随机端口后验证订单、库存与未发事件还在。

一键脚本按课程路径隔离Compose项目，只停止自己命名的服务，不扫描进程、不使用pkill、不删除卷。Linux命令边界回归覆盖11个情形，包括限定两个Java服务的SIGKILL、合法操作、非法服务名、命令注入字符串、不存在台账和未知检查点。scripts/recovery-check.py还提供订单进程与配送进程的SIGKILL、重建和原身份重放；只作用于本课程两个应用容器。macOS真实Compose尚未亲测，不能由可移植命令静态推断已通过。

## C14-05：审计、新变体与诚实答辩

学员实现O(n+m)审计：可售库存加仍预留数量等于初始库存；取消不计占用；负库存、不存在商品、无来源投影、同版本冲突或超前投影是ERROR；缺少/落后投影是LAG。累计采用long，输出不可变。页面使用同一REPEATABLE READ快照，避免把并发提交前后的两张表拼成假错误。

代表测试用固定种子构造100组预留/取消组合；真实集成另做未知响应、重复请求、取消、重放到第二消费组，并最终故意损坏独占测试数据的一件库存来验证审计会报警。

公开盲测题库包含4个故障、4个新需求和4个设计追问。脚本各随机抽一题；学员先独立编码，再看随时可读的参考解释。2分钟讲业务与不变量，5分钟加入事务/确认窗口和证据，15分钟加入源码、故障复盘、新变体及替代方案。不将教学实验改写成生产履历。

## 首轮CI发现的Kafka配置缺陷及修复

[首次CI 36738093924](https://github.com/weilhuang/backend-interview-labs/actions/runs/36738093924)在提交70af2cd8的快测与全部变体通过后，五个容器方法统一失败：初始化Admin只设置了default.api.timeout.ms=5000，却继承request.timeout.ms=30000。KafkaAdminClient在构造时拒绝总API预算小于单次请求预算，因此这次失败是公共初始化合同缺陷，不能解释成五个业务不变量分别失败。

现已统一应用主题初始化与集成位点检查的配置：总API预算5秒、单次请求2秒，外层等待6秒，关闭最多1秒；健康检查总预算1秒、单请求0.5秒，等待1.5秒，关闭最多0.5秒。没有通过无限增大超时隐藏问题。RealServices调用同一Broker.initialize，因此不另维护一份配置。

新增BrokerConfigTest三个无需Docker的真实客户端构造用例：旧配置确实抛ConfigException；两种正式Admin配置都可构造并有界关闭；现有Consumer配置同样可以构造和关闭。完整JDK21/Gradle本地快测从32增加至35，全部通过；所有容器测试类再编译，真实容器复测已在下述第二轮CI通过；本节保留首次缺陷与修复的历史记录。
