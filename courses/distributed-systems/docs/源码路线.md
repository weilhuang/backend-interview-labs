# 固定源码路线与观察记录

本页不是上游源码全文抄录。每个链接由官方标签解析到提交，并获取真实文件后记录SHA-256；完整机器可读证据在`authoring/source-verification.json`。下面的行号以该固定提交为准，升级不得沿用旧分支结论。

## gRPC：截止真正在哪里取最小值

- 版本1.71.0，提交`865c4432569dfdf738b3cf07bcdb6d6e3285f761`
- 入口：`ClientCallImpl.startInternal`，先计算有效deadline，再创建取消处理器、创建stream并设置deadline
- 核心：[ClientCallImpl.effectiveDeadline，424–426行](https://github.com/grpc/grpc-java/blob/865c4432569dfdf738b3cf07bcdb6d6e3285f761/core/src/main/java/io/grpc/internal/ClientCallImpl.java#L424-L426)，显式取CallOptions与Context截止较小值
- 对应实验：网关给下游8秒上限，上游只给4秒，最终库存响应剩余时间不大于4秒
- 反例：新线程丢掉Context后仅设置8秒，会失去这个跨跳约束；传播trace字符串本身不会自动传播Context
- 继续读：`ClientCalls`调用阻塞/异步observer，`ServerCalls.ServerCallStreamObserverImpl`的ready/cancel回调，以及`RetriableStream`的commit与retry分支
- 面试追问：客户端停止等待与数据库提交是两个边界，不能从截止错误推导库存未改变

## Dubbo：发现、选择与一次调用

- 版本3.3.6，提交`f1585880bee4ca7776f44380c47c994217721ffe`
- 路径：ReferenceConfig初始化代理 → RegistryDirectory接收地址 → cluster选择Invoker → 协议远程调用 → provider filter → 接口实现
- [ReferenceConfig](https://github.com/apache/dubbo/blob/f1585880bee4ca7776f44380c47c994217721ffe/dubbo-config/dubbo-config-api/src/main/java/org/apache/dubbo/config/ReferenceConfig.java)：观察get/init/createProxy，不把代理对象当作提供者本身
- [FailoverClusterInvoker.doInvoke](https://github.com/apache/dubbo/blob/f1585880bee4ca7776f44380c47c994217721ffe/dubbo-cluster/src/main/java/org/apache/dubbo/rpc/cluster/support/FailoverClusterInvoker.java#L59)：读取重试次数、选择未尝试/可用Invoker、记录业务异常与重试失败。课中选择failfast，外层只读循环自己控制总预算
- [ZookeeperRegistry](https://github.com/apache/dubbo/blob/f1585880bee4ca7776f44380c47c994217721ffe/dubbo-registry/dubbo-registry-zookeeper/src/main/java/org/apache/dubbo/registry/zookeeper/ZookeeperRegistry.java)：注册、订阅和通知是控制面，业务字节不经ZooKeeper转发
- [ContextFilter](https://github.com/apache/dubbo/blob/f1585880bee4ca7776f44380c47c994217721ffe/dubbo-rpc/dubbo-rpc-api/src/main/java/org/apache/dubbo/rpc/filter/ContextFilter.java)：附件传递/清理作用在哪一侧，为什么应用finally仍需清理client attachment
- 实际调试发现：127.*被NetUtils视为无效公布地址后改选网卡；本课程固定`::1`回环并使用独立FrameworkModel，验证了不会误走injvm
- 不推广：单节点ZooKeeper和本地进程退出不证明生产多数派、会话故障和多机灾难恢复

## Resilience4j：状态机与许可不是同一计数器

- 版本2.3.0，提交`c2c6575114fc0650177fb21e1ff967f14acde39c`
- [CircuitBreakerStateMachine](https://github.com/resilience4j/resilience4j/blob/c2c6575114fc0650177fb21e1ff967f14acde39c/resilience4j-circuitbreaker/src/main/java/io/github/resilience4j/circuitbreaker/internal/CircuitBreakerStateMachine.java)：外层tryAcquirePermission委托当前state；OpenState按等待截止决定是否进入半开；HalfOpenState限制探测数
- 课堂显式调用transitionToHalfOpenState以消除真实时钟抖动，不把这个动作包装成定时调度实证
- [SemaphoreBulkhead](https://github.com/resilience4j/resilience4j/blob/c2c6575114fc0650177fb21e1ff967f14acde39c/resilience4j-bulkhead/src/main/java/io/github/resilience4j/bulkhead/internal/SemaphoreBulkhead.java)：许可获取、拒绝事件、完成释放与最大等待预算
- 证据：保持2个在途请求时第三个立即拒绝；这个拒绝不进入内层breaker的失败统计
- 反例：把bulkhead放在breaker里面会改变统计含义；熔断器CLOSED不能保护数据库不受并发冲击

## MySQL Connector/J：XA不是普通commit的别名

- 版本9.2.0，提交`a3909bfeb62d5a517ab444bb88ba7ecf26100297`
- [MysqlXAConnection](https://github.com/mysql/mysql-connector-j/blob/a3909bfeb62d5a517ab444bb88ba7ecf26100297/src/main/user-impl/java/com/mysql/cj/jdbc/MysqlXAConnection.java)：prepare映射XA PREPARE，commit根据onePhase选择分支；recover执行XA RECOVER并解析formatId/gtrid/bqual
- 阅读点：106行recover入口、158行实际XA RECOVER、211行prepare、286行commit
- 实验用两个真正MySQL资源，不把同一连接两个逻辑方法称为分布式事务。日志必须先force成功再发送提交
- 8.4 detached XA允许准备后换连接恢复；账号权限、全局ID与分支ID约束按[官方8.4状态文档](https://dev.mysql.com/doc/refman/8.4/en/xa-states.html)检查
- 反例：协调日志丢失时不能根据余额猜决策；日志存在时不能重新执行同一次转账，只能恢复

## Kafka：传输重试与业务重复各自在哪里

- 版本3.9.1，提交`f745dfdcee2b9851204ddbbcd423626ab87294bc`
- [Sender](https://github.com/apache/kafka/blob/f745dfdcee2b9851204ddbbcd423626ab87294bc/clients/src/main/java/org/apache/kafka/clients/producer/internals/Sender.java)：批次发送、响应、失败重试与delivery timeout
- [TransactionManager](https://github.com/apache/kafka/blob/f745dfdcee2b9851204ddbbcd423626ab87294bc/clients/src/main/java/org/apache/kafka/clients/producer/internals/TransactionManager.java)：producer身份、序号和相关状态。配置enable.idempotence并不为MySQL事务创建共同提交点
- 证据：发送确认后、outbox标记前故障，关闭旧生产者并创建新生产者后重发同一事件，消费得到两条逻辑记录，inbox只让业务效果生效一次
- 反例：发布成功后立即删除outbox但数据库提交不确定、或消费先插入inbox再另开事务更新投影，都会打开丢事件/丢效果窗口

## Redis/Jedis：脚本原子性与版本前提

- Redis7.4.7，提交`4d1a341aaf0b96f9d2c43418efac732e31dc28ad`；Jedis5.2.0，提交`54426424a21070bba3b12454e48aa692efc3a9fa`
- [Redis evalGenericCommand](https://github.com/redis/redis/blob/4d1a341aaf0b96f9d2c43418efac732e31dc28ad/src/eval.c#L551)：准备脚本运行环境、执行和返回；[db.c](https://github.com/redis/redis/blob/4d1a341aaf0b96f9d2c43418efac732e31dc28ad/src/db.c)观察键查找、修改与失效相关操作
- [Jedis.eval](https://github.com/redis/jedis/blob/54426424a21070bba3b12454e48aa692efc3a9fa/src/main/java/redis/clients/jedis/Jedis.java)只是提交脚本与KEYS/ARGV，真正的原子执行由Redis负责
- 本课fill的检查与写值在同一个脚本内，invalidate的提升floor与删除旧值也在同一个脚本内
- 版本不超过2^53-1，避免Lua数字表示损失整数精度；floor持久保留带来键基数成本
- 反例：Redis元数据丢失、跨槽执行、多主版本冲突、无界投影延迟均不能由这两个脚本自动解决
