# 保证边界与故障矩阵

## 先确定不可违反的性质

- 单MySQL主库中库存始终非负；库存扣减和操作终态同一个事务
- 相同业务键、相同参数只产生一次库存效果；相同键不同参数拒绝
- 租约接管后旧owner/代次不能提交；租约时间由同一数据库时钟判定
- TCC总量available+reserved+sold守恒；重复取消不重复归还，空取消阻止晚到Try
- Saga的每项参与者效果幂等；本地提交到协调检查点之间允许崩溃并可恢复
- XA两个资源的恢复只根据持久化决策，不根据余额猜测；日志丢失超出承诺
- outbox与业务原子提交，发布允许重复；inbox与读模型原子提交，版本不后退
- RPC截止限制调用等待，不声称取消了已经完成的数据库提交

## 可执行故障点

| 故障点 | 立即可观察结果 | 恢复与测试入口 | 不承诺的内容 |
|---|---|---|---|
| 服务已提交、响应丢失 | 客户端UNKNOWN | C10-01模型；C10-05查询原键 | 超时自动回滚 |
| gRPC等待超过deadline | DEADLINE_EXCEEDED，服务端取消监听释放挂起计数 | GrpcTest截止取消 | 杀死任意业务线程/SQL |
| Dubbo提供者退出 | 短期RPC失败，发现目录更新后另一个节点可用 | DiscoveryTest/DubboTest | 注册中心单节点HA、无中断故障转移 |
| 输入超限 | INVALID_ARGUMENT或业务参数拒绝 | gRPC/Dubbo测试 | 仅靠客户端校验安全 |
| 超过准入/隔离额度 | 立即拒绝，无无限队列 | CapacityTest/Resilience LabTest | 全局公平或全局额度 |
| 同键并发 | 一个OWNED，其余BUSY/REPLAY | MySqlIdempotencyTest | 依赖JVM synchronized跨节点仲裁 |
| 领取后进程丢失 | PENDING保持，租约后可接管 | IdempotencyTest/MySQL集成 | 永久持有锁或无限延租 |
| 扣库存后结果未提交 | 事务回滚 | 单元故障点、MySQL关闭未提交连接 | 外部支付自动回滚 |
| TCC Cancel早到 | CANCELLED墓碑，晚到Try拒绝 | TransactionTest空回滚 | 墓碑删除后仍能阻止任意晚消息 |
| Saga远端成功日志未写 | 参与者成功、协调仍旧态 | 重建Saga重放同键 | 参与者与协调日志全局原子 |
| Saga退款后释放前失败 | COMPENSATING留存，再次退款幂等 | 补偿失败测试 | 补偿绝不会失败/自动人工处理 |
| XA准备后协调消失 | 准备分支持久化，可能持锁 | 两MySQL资源recover | 协调日志复制/自动选主 |
| Kafka ACK后outbox标记前崩溃 | 重发产生2条逻辑消息 | OutboxIntegrationTest | 端到端exactly once |
| inbox提交前失败 | inbox和投影均回滚 | ProjectionTest | H2证明MySQL全部锁语义 |
| Redis失效前进程崩溃 | DB更新已完成，缓存可能暂时旧 | 重复消费也再次失效 | 无延迟上界的“立即一致” |
| 旧查询在失效后回填 | floor拒绝旧版本 | Redis真实Lua集成 | floor丢失后永久拒旧 |

## 缓存时间边界不能省略前提

当前示例的floor键不随缓存值过期。它防止相同Redis状态时代的版本倒退，需要限制合法SKU集合并配置监控/清理，不允许任意用户生成无限key。

- 从主库读取且每次读取最长Q、缓存TTL为T：一个更新前开始的旧读取最多在Q内完成，再存留T，因此可用Q+T描述该类旧值的保守上限
- 若填充来源是异步投影，还需投影延迟上界L，可讨论L+Q+T；如果消息永久积压没有L，就不能给有限陈旧度承诺
- Redis重建/故障切换丢失floor后，旧回填保护降级；TTL仍需真正执行，客户端不得无限续旧值
- 数据库从旧备份恢复、全局版本重置或多主冲突不在当前单调版本保证内，必须停流核对epoch并重建读模型
- Redis Cluster跨槽Lua不原子且会报错。本课使用单节点；扩展必须将floor和value放在同hash tag，并重新测试

## 过载与故障预算设计评审

1. 分开记录入口速率、接受率、在途、排队、数据库连接、锁等待、RPC attempt、成功/错误率与分位数
2. 把total deadline分给本地计算/连接获取/下游/响应预留，retry每次消耗同一预算
3. 限流/隔离拒绝不自动计入下游故障率；业务不足不重试，网络未知写按原业务键恢复
4. 注册中心不可用时已有地址可继续使用，但不能假设新节点发现正常；缓存失败时保护数据库而非全量无界回源
5. outbox积压提高可见延迟，需积压条数/最老年龄/重复率/毒消息告警。教学没有后台无限重试服务，运行者必须执行并观察驱动
6. 两MySQL XA实验只能说明prepare/recover协议；生产协调器的日志复制、选主、重试与人工启发式决策需另行验收
7. 降级不能伪造关键交易成功。列表可显示暂时不可用/旧数据提示；结算库存不确定应拒绝或返回待确认状态

## 独立答辩评分

- 30分：代码和可复现实验，所有不变量有正例/边界/故障证据
- 25分：每个提交窗口的恢复策略与幂等作用域
- 20分：固定源码符号、状态与真实框架行为，区分教学模型
- 15分：容量与故障预算、热点/分片/异地取舍
- 10分：现场迁移与表达，不靠背诵口号

评分是练习反馈，不保证面试结果。隐瞒未执行Docker/GUI验证、删除断言或只扩大超时不算通过。

## 发现实验的明确运行环境

Dubbo3.3.6会把127.*主机配置视为无效地址并自动选网卡。本课为保证只在本机暴露，使用明确IPv6回环`::1`，而不是跟随容器内可能不可达的网卡地址。没有修改系统网卡、路由或防火墙；环境若没有IPv6回环，需要在受支持测试环境运行，不能静默绑定公网地址。提供者/消费者各持有独立FrameworkModel，关闭时销毁各自线程与注册资源，避免同一全局应用配置冲突。

测试中禁用Dubbo持久地址文件缓存，防止向用户主目录写入文件。因此本课注册中心失联时的“内存已有地址可继续使用”与“进程重启后读磁盘缓存”是两件事，后者未由此测试证明。
