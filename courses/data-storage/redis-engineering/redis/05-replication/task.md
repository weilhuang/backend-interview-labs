# C07-05 持久化、复制与手工故障转移

## 企业场景与进入条件

缓存节点重启以后哪些数据还在？主节点确认写入是否代表副本拿到？主节点失联后应用如何切到副本而不产生两个可写主？本节让服务端进程真正停止/重启，并启动同源镜像的两节点复制。先理解C07-01命令、C07-04事实库和最终一致性。

A验证RDB/AOF约定配置的进程崩溃恢复、真实复制链路和手工提升；O解释持久化、复制与确认差异；R定位Redis持久化和复制核心路径。不是Sentinel/Cluster自动选举完整实现，也不以单节点实验声称高可用。本云端没有Docker daemon，因此作者报告只记录编译通过，真实故障结果待运行。

## 概念、例子与ASCII

```text
RDB：内存状态 -- SAVE/BGSAVE --> 某时刻快照文件
AOF：写命令   -- 追加缓冲 --> 文件write --> fsync策略
复制：主节点  -- 复制流/offset --> 副本确认

客户端SET返回       不等于       副本确认/所有介质抗断电
同连接WAIT(1,5000)  ------->      等待此前写入的副本offset确认

主节点停止并隔离 -> 确认副本状态 -> REPLICAOF NO ONE -> 应用换端点
旧主保持隔离 ------------------------------------> 防止双写
```

RDB实验显式SAVE写入“快照内”，再写“快照后”，关闭自动save和AOF，SIGKILL服务端后在同一容器文件系统重启。预期读取“快照内”。AOF实验配置appendonly=yes、appendfsync=always，SET已确认后SIGKILL，再读“已确认”。这里测的是进程崩溃，不是拔掉电源、磁盘控制器欺骗fsync、持久卷丢失或整个宿主机灾难。

复制是异步基础模型，WAIT返回指定副本确认数能增强某次写入的可观测安全程度，但不是共识提交证明，也不是所有副本磁盘fsync确认。WAIT必须放在同一写连接，不能换一条无写历史的连接后凭返回值解释之前那次写。超时返回数量不足时，写入结果可能仍存在，不可直接当没写而重试非幂等业务。

## 编码步骤与调用验证

1. 运行`./gradlew :redis:05-replication:unitTest`，解析INFO的section、空行、值内冒号。INFO用于观察，不依赖字段顺序
2. 运行`./gradlew :redis:05-replication:run`。调用端启动专用Network与主/副本容器；观察master_link_status=up，同连接SET/WAIT，再停止旧主、提升副本并显示角色。只对本次创建容器发SIGKILL
3. 编辑`src/labs/Replication.java`的`promoteIsolatedReplica`实现区：确认目标目前是副本，调用REPLICAOF NO ONE，再验证角色变成master。方法名前提“已隔离旧主”不是装饰，调用者必须先做到
4. 运行`./gradlew :redis:05-replication:test`。RDB/AOF分别起不同实例，无宿主机挂载，避免跨测试残留；重启保留同一容器的/data，关闭测试后容器销毁
5. 双节点测试明确等待复制链路up；主连接写后WAIT返回1；副本读取同值；旧主停止后客户端ping报错；提升副本后写入新值。旧主在测试结束前不恢复为可写节点
6. 另存一份O报告：SET确认时刻、WAIT结果、主从复制offset、角色、配置、失败类别和恢复操作。不要把这几个动作合并成“Redis高可用已证明”一句话

## 标准解逐步解释与边界

[完整公开标准解](solution.md)。info按首个冒号切分，保留复杂值；提升前后都检查role，避免对错误节点盲发命令。RedisLab持有自己创建容器的ID，崩溃与启动只作用该ID；两节点镜像都从同一Images读取器取REDIS_IMAGE，无重复版本常量。

等待函数有15秒总预算和25毫秒轮询间隔，轮询仅观察外部服务状态，不用于“睡够就认为复制完成”。失败明确超时，保留错误定位；这不是性能达标阈值。复制初次同步需要时间和内存资源，在极慢环境可以依据证据调整测试环境预算，不能删除复制断言。

RDB快照频率决定恢复点，AOF重写不是把所有历史无限保留；appendfsync每秒模式有不同的持久化窗口，本课不靠一次机器测试估计所有极端损失。主从复制延迟、复制积压缓冲和全量同步影响恢复成本，数据文件存在也不等于文件可恢复，应实际加载校验。

本节只有手工提升。生产自动故障转移还需要故障检测、仲裁、配置传播、客户端拓扑刷新和旧主隔离。Redis Cluster把键映射到16384个hash slot；分片解决容量/路由，复制副本解决另一类可用性问题，不能把“开Cluster”当线性一致承诺。跨slot Lua限制与业务实体键设计相关。

## 真实源码阅读路线

固定Redis **7.4.7**：

- [src/rdb.c](https://github.com/redis/redis/blob/7.4.7/src/rdb.c) `rdbSaveBackground`：fork、子进程保存、状态与完成回收路径；SAVE与BGSAVE区别不能只背“同步/异步”而不解释谁承担工作
- [src/aof.c](https://github.com/redis/redis/blob/7.4.7/src/aof.c) `flushAppendOnlyFile`：缓冲写出与fsync策略分支，指出write完成不是任意硬件上的持久化证明
- [src/replication.c](https://github.com/redis/redis/blob/7.4.7/src/replication.c) `waitCommand`、`replicationCountAcksByOffset`、`replicaofCommand`：等待的offset、超时返回与角色切换
- [官方WAIT命令](https://redis.io/docs/latest/commands/wait/)帮助核对保证范围；不要把更新后的说明替代固定源码与运行配置

阅读路径已核验，服务端调试断点和真实容器输出尚需学习环境补证。

## 面试问题、答案与追问

1. **RDB和AOF是否二选一？** 可以组合，恢复选择和配置需核对目标版本；本实验分开是为了隔离变量，不代表生产必选一种
2. **WAIT=1是否零丢失？** 不能这样承诺。它确认复制接收程度，不能消除所有持久化、选主、故障组合；追问副本随后也丢盘如何处理
3. **主宕了提升副本就完成了吗？** 还需旧主隔离、客户端切换、数据差异检查和恢复拓扑。故障检测误判时两主并存尤其危险
4. **缓存为什么还要持久化？** 可能降低冷启动回源洪峰、恢复昂贵派生数据，但需明确事实来源、恢复时效和陈旧风险；不应为了“有AOF”让Redis成为未经设计的唯一账本
5. **分片和复制有什么区别？** 分片分担键空间，复制提供同一分片副本；热单键仍落在一个slot，节点数量变多不自动解决单键瓶颈

## 独立迁移与退出评阅

在提升后让旧主以副本身份重新加入，必须先确认无法对外提供写入；记录全量/部分同步与数据校验。再设计WAIT返回0的处理契约，说明结果未知如何查证而非无脑重试。A需真实双节点和重启结果，O需故障范围声明，R需函数、状态和分支；如果没有Docker，仅完成源码与协议设计，不标记动态演练通过。
