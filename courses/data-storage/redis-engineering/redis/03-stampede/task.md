# C07-03 穿透、击穿与雪崩

## 企业场景与进入条件

促销期间三类负载同时出现：随机查询不存在的订单；一个热门活动键刚过期；大批商品在整点一起失效。数据库连接有限，不能把“Redis没命中就直接查库”当完整策略。先会CompletableFuture、锁、超时和C07-02TTL。本课实现单进程单飞、短负缓存和过期抖动，并验证失败释放与不同键容量上限。

A包含真实Redis负缓存/并发调用；T是Java单飞协议，不模拟Redis服务器；O讨论多实例扩展和Bloom过滤边界。回源固定函数的测试不等同于真实数据库容量证明，真实MySQL服务组合在C07-07。

## 概念、例子与ASCII

```text
穿透：很多不同的不存在ID -> Redis miss -> DB空结果 * N
      修复：短负缓存 / 经评估的存在性过滤
击穿：一个热门ID过期 -> 同一时刻 N个回源
      修复：同键单飞，共享一份Future
雪崩：大量ID在同一时刻过期 / Redis整体不可用
      修复：TTL抖动 + 回源并发预算 + 降级

请求A -> flights[k]不存在 -> 登记Future -> 回源 -> 完成 -> finally移除
请求B -> flights[k]已存在 ---------------------> 有界等待相同Future
请求C -> 新key且容量满 -> 明确拒绝，不占无界队列
```

缓存编码n:表示“不存在”，v:后面才是普通值，因此合法字符串n:不会误判成缺失。不存在订单连续读8次，回源计数应为1，负缓存TTL不超过2秒；商品被创建后删除该键，就能读到新值。负缓存降低重复不存在ID压力，但不防止无限随机ID造成键空间膨胀，容量保护仍然必需。

TTL10秒、抖动20%，取值限定8到12秒。固定种子用来重现边界，不声称随机分布天然解决全部雪崩。Redis整体不可用时抖动没有作用，必须有回源保护。

## 编码步骤与调用验证

1. 运行`./gradlew :redis:03-stampede:run`，看到三次读取只有首次打印回源。读`StampedeUsage`，其回源是明确标注的Optional.empty fixture
2. 运行`./gradlew :redis:03-stampede:unitTest`，先观察同键所有者/跟随者测试。进入`src/labs/Stampede.java`的`load`实现区，不要把慢loader放进synchronized块
3. 在锁内查找Future；只有新键所有者占一个容量槽；满容量拒绝新键，但已有键仍可加入等待。锁外执行loader/等待，finally按同一个Future移除，不能误删下一轮任务
4. 所有者失败时completeExceptionally，跟随者应获知原因；等待超时不能取消别人共享的加载。测试以latch固定所有者进入，用waiting状态确认跟随者已加入，再释放，严格断言一次回源，不靠sleep猜调度
5. 运行`./gradlew :redis:03-stampede:test`，4个线程各借独占Jedis连接，真实Redis缺失之后加入一个单飞。Jedis本身不是线程安全对象，不可在多个线程共享同一个实例；Supplier返回的连接由方法关闭
6. 检查负缓存TTL、合法值n:、失败后inFlight回到0。增加“某跟随者中断，其他调用仍能结束”回归，并保持最终无遗留任务

## 标准解逐步解释与边界

[完整公开标准解](solution.md)。HashMap的登记/检查受同一monitor保护；耗时操作不持锁；CompletableFuture共享结果与异常；不同键上限防止容器无限增长。命中缓存直接返回，失效后单飞所有者再次查Redis，避免刚刚被其他线程写入的结果再次回源。回源期间不占Redis连接，写回再借一条独占连接。

HashMap查找平均O(1)，内存O(并发不同键数)，每个跟随者仍占调用栈和等待资源。所有者同步执行loader，单飞的wait预算只限制跟随者，不能终止卡死的所有者；loader必须有数据库/网络自身超时。C07-07再把执行器和回源预算补齐。只把CompletableFuture.get加超时不能证明底层取消。

JVM内单飞不跨实例。十个应用实例各自一次回源仍可能产生十次数据库查询；可接受时不要无谓引入分布式锁。跨进程互斥需要租约、失败恢复、锁过期持有者保护和锁服务自身可用性，C07-06单独展开。负缓存要短期限，必要时与新增事件失效联动。

## 真实源码与机制边界

本节单飞是T应用协议，**不是Redis自带singleflight实现**，因此不伪造一个Redis单飞源码函数。真实服务侧继续定位Redis **7.4.7** [src/t_string.c](https://github.com/redis/redis/blob/7.4.7/src/t_string.c)的`setGenericCommand`：观察SET PX如何把值和过期状态关联；[src/db.c](https://github.com/redis/redis/blob/7.4.7/src/db.c)的读取路径解释失效后为什么返回缺失。

JVM机制阅读固定[OpenJDK21+35 CompletableFuture.java](https://github.com/openjdk/jdk/blob/jdk-21%2B35/src/java.base/share/classes/java/util/concurrent/CompletableFuture.java)，从`get(long, TimeUnit)`的等待/超时路径与`completeExceptionally`对照本测试。源码阅读支持机制解释，不能替代多线程测试的可控时序证据。

## 面试问题、答案与递进追问

1. **三类缓存故障区别？** 穿透看大量不存在键，击穿看单个热键失效，雪崩看大批键/服务整体失效。指标应观察miss键分布和回源并发，不用一个“缓存穿透”概括全部
2. **负缓存会让新订单不可见吗？** 会有负缓存窗口，需短TTL或创建后失效；敏感的读己之写可绕过缓存。追问乱序事件要带版本，见下一节
3. **为什么失败一定清理Future？** 否则之后所有请求永远复用已失败Future，单次事故变永久故障；finally清理并保持异常可见，不能吞异常返回假成功
4. **Bloom filter为什么不能直接删除？** 普通Bloom位被多个元素共享，清除一位可能制造假阴性；Counting Bloom需计数及溢出/并发治理。误判意味着可能多回源，并非“不存在一定精确识别”，重建与数据同步也有成本
5. **超时跟随者可以cancel共享Future吗？** 不应默认这样做，它无权终止其他调用仍在等待的工作。先明确所有权和取消传播；单个请求deadline与共享任务生命周期不同

## 独立迁移与退出评阅

把最大不同键数改为2，同时有a、a、b、c请求：a只回源一次，b可并行，c立即拒绝。再让a所有者失败，证明a之后可以重试而不是永久失败。最后设计两个实例各自单飞的负载估算，解释是否值得加分布式锁。A要求严格次数与释放不变量，T需列出省略的跨进程能力，O需说明随机ID攻击下负缓存的容量问题。
