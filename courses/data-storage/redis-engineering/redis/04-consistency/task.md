# C07-04 数据库与缓存的竞态

## 企业场景与进入条件

商品价格事实写入MySQL，详情页优先读Redis。要求写库失败不能发布成功失效事件；Redis删除失败、发布进程重启、旧读者延迟回填都必须能解释并恢复。先完成C06事务和C07命令。这里是最终一致缓存，不承担付款时价格确认；关键交易读取事实库并验证版本。

本节A使用真实MySQL JDBC和真实Redis，没有H2或Java Map冒充数据库。可控时序采用明确暂停点后的顺序调用，精确重现两个逻辑请求的交错，不靠概率压测“碰到一次”。T只存在于故障注入回调，数据库提交和Lua执行都是真实服务行为。

## 概念、例子与ASCII

```text
旧读者A                   写者B                     Redis
读取DB v1（暂停）
                         事务写商品v2 + outbox
                         commit
                         删除缓存 -----------------> 空
A恢复，填v1 ---------------------------------------> v1（已旧）

可靠失效器：读待发outbox -> Lua提高floor至2 + 删除<=2缓存 -> DB确认
晚到v1再次回填 ------------------------------------> floor=2，拒绝
Redis清空/淘汰floor -> 暂停读流量 -> 从DB重建所有floor -> 开放流量
```

“先更新数据库再删除缓存”仍有旧值回填窗口，也有删除失败窗口。延迟双删选择某个等待时间只能缓解特定延迟分布，不能排除无限暂停读者。解决方案需要声明故障模型：本节商品版本单调递增，商品事实与outbox同一MySQL事务提交；服务端Lua用版本水位防旧填；失效器至少一次投递并可重发。数据库是事实来源，Redis水位不是备份。

Product编码使用`版本|Base64(UTF-8值)`，值包含竖线/中文也不破坏头部。版本限定1至2^53-1，以免Lua数字比较损失整数精度。两个Redis键含同一`{商品ID}`，为迁移Cluster同槽Lua作准备，本节仍是单节点实例，不伪装成Cluster实验。

## 编码步骤与调用验证

1. 运行`./gradlew :redis:04-consistency:run`，启动隔离MySQL和Redis，看到初读、待发事件数1、恢复后新值。表只建在临时c07_lab，关闭容器后删除，不操作共享业务库
2. 运行`./gradlew :redis:04-consistency:unitTest`，验证中文/分隔符编解码、版本精度边界、回滚失败不会覆盖最初异常。阅读`Consistency.Store`中的事务，不把设置autoCommit(true)当回滚
3. 编辑`src/labs/Consistency.java`的`fill`实现区：校验TTL；Lua读取floor，拒绝incoming<floor；读取已缓存版本，拒绝覆盖更高版本；用SET PX写入并返回是否接收。键放KEYS，数值/编码放ARGV
4. 运行`./gradlew :redis:04-consistency:test`的旧回填用例。先读v1，再提交v2+outbox，再删除，再回填v1，此时测试故意断言读到旧值，证明反例真实存在
5. `recover`发送Lua后、数据库ack前抛异常，检查事件仍待发；创建新Store对象模拟发布器重启，重发后pending=0。Lua必须幂等且旧事件不能降低floor或删除更新版本
6. 测试Redis进程实际崩溃导致发送失败，确认MySQL事件未消失；重启连接后调用恢复。每批limit为1至1000，示例一个事件一批完成；没有后台定时器时不会凭空自动恢复
7. 测试所有待发事件已确认后Redis无持久化崩溃：水位也丢失，旧填会重新成功。保持应用readiness关闭，从DB重建本fixture唯一商品的水位，再开放读取。真实系统要分页遍历全量对象或采用经过设计的纪元方案

## 标准解逐步解释与一致性边界

[完整公开标准解](solution.md)。update用SELECT FOR UPDATE锁住商品版本，再修改事实并插入outbox；任何错误回滚两者。rollback若也失败，用suppressed保留根因。recover先执行幂等外部动作再标记delivered，发送成功ack失败时会重复而不会静默丢失。批量上限控制一次工作量，pending提供积压观测。

fill的两个比较各有职责：floor抵御已知失效之前的旧快照；当前cache.version避免两个读者不同顺序回填导致倒退。invalidate只把floor抬高，且只删除不比事件更新的缓存。即便fill被拒绝，当前读者手里已经读取的旧DB快照仍可作为其响应返回；本实现没有给“写完成后所有在途读都返回新值”的线性一致承诺。

恢复时限由发现失败、重试调度、Redis恢复、MySQL可用、积压批数共同决定。本测试证明显式重试一次/有限批数能收敛，不宣称无人调用recover仍有固定秒级上界。生产需监控pending最老年龄、重试次数和失败率，安排有界退避，不无限密集重试。

水位无TTL仍可能被allkeys策略淘汰，也可能在灾难/异步副本切换中丢失。应隔离到不淘汰的状态域并有容量策略，或停流重建；长期无界保留水位需要商品删除/tombstone生命周期协议，本课fixture一个商品避免隐藏增长。故障恢复窗口必须限制旧加载寿命或保留水位，不能仅说“最终TTL到了就好”。

复杂度：单商品DB行锁更新O(索引定位)，Lua固定两键O(1)，恢复每批O(limit)。多发布器可重复发送，版本逻辑仍安全，但本例没实现抢占调度、租约分片、事件归档、CDC和海量索引优化，不能称生产完整outbox平台。键命名空间只允许本协议写入合法编码；若被污染，应告警并定点修复后重放，不把所有运行时错误永久盲目重试。

## 真实源码阅读

固定Redis **7.4.7** [src/eval.c](https://github.com/redis/redis/blob/7.4.7/src/eval.c)的`evalGenericCommand`与[src/t_string.c](https://github.com/redis/redis/blob/7.4.7/src/t_string.c)的`setGenericCommand`，定位脚本隔离、返回和SET期限路径。MySQL事务基础参考[官方InnoDB事务模型](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-model.html)，具体双资源协议由本Java实现定义，不存在“一条Redis源码保证MySQL和Redis原子提交”。R报告必须分别写出服务内原子边界和服务间非原子边界。

## 面试问题与追问

1. **更新库后删缓存为什么仍旧？** 已读旧DB的A可晚于删除回填；用本时间线说明，不用泛泛说“并发有问题”
2. **删除失败怎么补？** 与事实同事务持久化待发事件，再幂等重试。仅内存队列在进程退出时会丢；追问事务提交响应未知时用持久状态查证，不凭超时认定回滚
3. **版本比较能解决所有一致性吗？** 不能，版本必须单调、比较精确、状态不丢且所有写入遵循协议；在途读响应、复制延迟和水位淘汰有独立边界
4. **为什么ack放发送后？** 先ack再发送会出现永久丢失；后ack允许重复，所以失效接收必须幂等。支付/邮件等非幂等动作还需专门去重协议
5. **水位不设TTL就是永久可靠吗？** 不是。no-TTL和持久性是不同属性，淘汰/重启/切主都可能损失，需要重建流程及流量门禁

## 独立迁移与退出评阅

增加商品删除与重建，不能把版本从1重新开始；用tombstone或新纪元区分旧生命周期。加入v3事件先到、v2后到，证明缓存/水位不后退。提交A全链路、O故障假设与恢复时限公式、R服务内边界；如果只交“更新后删除”一句话，或把服务启动/数据模型模拟当最终一致证据，则不通过。
