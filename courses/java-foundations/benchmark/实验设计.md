# 索引与缓存的JMH实验设计

依赖JMH1.37，仅JDK21，无其他JDK/应用。完整QueryBenchmark.java与benchmark/build.gradle均可见。默认测试不纳入此模块，在源码仓库路线显式运行./gradlew -PwithJmh :benchmark:jmh；Academy官方ZIP不保证含Wrapper，导入后改用IDE Gradle工具窗口或回到完整源码目录。

## 可回答的问题

同一不可变订单集合下，全扫描与客户索引在轮转查询时有什么时间/分配差异？热缓存命中的成本是多少？本实验不测动态更新、并发争用、数据库或网络，不外推生产延迟。

数据固定seed108，规模128/4096、64个客户、0..99分金额，所有Order不可变。scanRotating和indexedRotating使用相同轮转(customer,minimum)分布并按ID排序，语义由IndexedOrdersTest差分验证。轮转集合远大于LRU16，重点看未命中路径。cachedHotKey是单独的热键实验，不冒充与随机扫描相同负载。

## 受控参数与结果

一个fork、一个线程、2次500ms预热、3次500ms测量；这是快速可运行起点，尾部或微小差异须增加fork/样本后再谈结论。默认平均耗时，结果以JSON保存在benchmark/build/jmh-result.json。返回List由JMH消费，不手写空循环当微基准；构造成本在Trial setup外，不应把结论说成“包括索引构建也免费”。

报告JDK发行商完整版本、CPU/架构、堆、JMH版本、参数、样本、误差与是否加GC profiler。要观测分配可在明确单独实验中启用-prof gc；报告观察而不是“必须快X倍”自动门槛。

## 结论边界

算法复杂度来自操作数与不变量，不是某台机器一次计时。小N全扫描可能有局部性优势；索引占额外内存，热缓存与冷查询不是同一种工作负载。若依赖下载或运行失败，保留BLOCKED/NOT_RUN；没有结果文件不得编造图表。更新与线程安全是迁移题，当前类明确不提供。
